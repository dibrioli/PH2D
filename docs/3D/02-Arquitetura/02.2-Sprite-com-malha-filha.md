# O objeto misto: sprite pai, malha 3D filha

## O pedido, literal

> *"o objeto será uma sprite que tem como filho uma malha 3D que emprestará à sprite o seu shader
> avançado. Esse objeto misto rodará em runtime com iluminação 3d avançada, embora em 2d."*

## O modelo

```
Entity  "Herói"                     ← Sprite (o que o jogador vê)
├─ Sprite { texture, rect, … }
├─ Transform
└─ Entity  "Herói/forma"            ← FILHA na MESMA hierarquia ECS
   ├─ Mesh3D { asset, camera }      ← a malha esculpida
   ├─ MeshShading { sss, ao, cavity, material }
   └─ Transform                     ← pose da forma relativa ao sprite
```

**Uma hierarquia só.** É o norte do [ADR-0110](../../architecture/decisions/0110-vector-nodes-are-ecs-entities-one-hierarchy.md)
(*todo path vetorial é uma entidade ECS; árvore única*) aplicado à malha: a forma herda seleção, nome,
parentesco, delete, undo e save **de graça**, e o artista a manipula com os gestos que já conhece.

⚠️ **A malha NUNCA é desenhada na tela diretamente.** Ela renderiza para um G-buffer fora de tela, do
tamanho do retângulo do sprite. Quem aparece é o sprite.

## O caminho de um frame

```
1. a malha filha rasteriza  →  G-buffer (normal · depth · AO · cavity · material · cover)
2. o sprite pai é sombreado  →  albedo do sprite × iluminação lida do G-buffer
3. composita no 2D de sempre
```

O passo 2 usa **o mesmo modelo de lâmpada do editor** (`ph2d-light`) ⇒ o que o artista viu pintando é
o que o jogador vê jogando. Isso não é elegância: é a única forma de o ajuste de luz feito na arte não
mentir em produção.

## As duas rotas de runtime

A decisão é **por objeto**, e ela espelha exatamente o [ADR-0131](../../architecture/decisions/0131-physics-global-runtime-truth-rapier-ecs-bridge.md)
da física (*runtime-truth + bake opcional*):

### Rota A — ASSADO (o padrão)

A pose da malha em relação ao sprite não muda em runtime (o caso esmagador: um objeto de cenário, um
item, um personagem em pose fixa por quadro de animação).

- O G-buffer é gerado **uma vez**, no editor ou no cook, e vira **canais do sprite**
  (`normal · depth · AO · cavity · material`).
- Em runtime **não existe malha nenhuma** — é um sprite com canais extras.
- Custo: o de um sprite normal-mapeado. **Roda em mobile.**
- A malha some do build do jogo se ninguém mais a usa.

### Rota B — AO VIVO (opt-in)

A forma gira, deforma ou é iluminada por algo que muda de geometria a cada frame.

- A malha filha rasteriza para o G-buffer por frame, com **dirty flag**: só re-renderiza se a pose, a
  malha ou a câmera mudaram.
- Custo: um passe de geometria por objeto vivo, no orçamento do HR-4.
- É o que permite **rotacionar um sprite e ver a luz acompanhar** — o efeito que nenhum sprite
  normal-mapeado comum consegue.

> **A rota A é o produto; a rota B é o luxo.** Quem escolhe é uma propriedade do objeto, e o editor
> mostra o custo das duas.

## O que isso destrava, e ninguém entrega

1. **Sprite girando com luz correta** — o normal map de um sprite comum é fixo; o nosso é re-derivado da
   forma real.
2. **Sombra de contato** entre sprite e cenário, vinda da profundidade real.
3. **Turnaround coerente em animação 2D** — a forma vira, o artista repinta por cima com a luz certa.
4. **SSS num sprite** — pele, cera, folha: o que faz um render parecer caro ([[05.1-Shader-de-runtime]]).

## Costuras com o que já existe

| Costura | Estado |
|---|---|
| Hierarquia ECS pai/filho | ✅ existe (`ph2d-ecs`, ADR-0110) |
| Sprite com material e blend | ✅ existe (Sprite Inspector v2, ADR-0074) |
| Rig de lâmpadas | ✅ existe no impasto; **promovido** a `ph2d-light` |
| Compositor de camadas | ✅ existe (`ph2d-render::layer_compositor`) |
| Render para textura fora de tela | ✅ existe (`game_rt.rs`, `preview_premul`) |
| Canais extras no sprite | ⚠️ **novo** — é a única extensão de dados do lado 2D |

- Quantos objetos em rota B cabem no orçamento? *(sonda da wave de runtime)*
