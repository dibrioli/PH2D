# Mobile GPU architecture and screen-space 2D lighting: what makes it fast or slow, and what wgpu 29 can reach

> Research date: 2026-10-08. The workspace pins `wgpu = "29.0.4"` (checked in `Cargo.lock`). wgpu v30.0.0 (2026-07-01) and v30.0.1 (2026-08-21) are already out; differences are noted where they matter.
> Arithmetic marked **[derived]** is mine, computed from the cited inputs. It is not a measurement.

## 1. Tile-based GPUs (Apple, Arm Mali, Qualcomm Adreno, PowerVR): why full-screen passes and read-backs are expensive

### Takeaway
On every major mobile GPU, a render pass draws into on-chip tile memory. That memory is much faster and costs far less energy than DRAM. The expensive steps are each `load` (DRAM → tile), each `store` (tile → DRAM) and each separate pass that samples the previous pass's output. Arm's rule of thumb is about **100 mW per GB/s** of DRAM traffic. A mobile SoC has roughly **5 W** and **about 30 GB/s** in total, against 300–500 W and about 300 GB/s on desktop. So the number of full-screen render targets written and re-read per frame is the first-order cost of a lighting design. ALU work comes second.

### Cited findings
**Apple (TBDR)**
- Apple GPUs split the render target into tiles, process each tile on one GPU core, and defer fragment work until all geometry for the tile has been evaluated. Fragments are written into "tile memory … fast, temporary storage that resides on the GPU itself". Tile memory has "bandwidth that's many times faster than device memory", "access latency that's many times lower" and "energy consumption that's significantly less". The final result is written to device memory only after the tile finishes. — [Apple, Tailor your apps for Apple GPUs and TBDR](https://developer.apple.com/documentation/metal/tailor-your-apps-for-apple-gpus-and-tile-based-deferred-rendering)
- On the same page, Apple says hidden-surface removal means only visible primitives are shaded. The vertex stage of the next pass can overlap the fragment stage of the current one. — [Apple](https://developer.apple.com/documentation/metal/tailor-your-apps-for-apple-gpus-and-tile-based-deferred-rendering)
- "Deferred shading is memory bandwidth intensive because the shaders write those textures to device memory in the first phase then read them back in the second." Apple's cure is to keep the G-buffer in tile-sized chunks and merge both phases with raster order groups. — [Apple](https://developer.apple.com/documentation/metal/tailor-your-apps-for-apple-gpus-and-tile-based-deferred-rendering)

**Arm Mali**
- Arm's planning estimate: "memory bandwidth has a direct correlation with power consumption, which can be estimated as 100 mW/(GB/s)". Worked example: 360 MB per render pass at 30 FPS is 10.8 GB/s, which is at least 1.08 W from memory traffic alone. — [Arm blog, Memory limits with Vulkan on Mali GPUs](https://developer.arm.com/community/arm-community-blogs/b/mobile-graphics-and-gaming-blog/posts/memory-limits-with-vulkan-on-mali-gpus)
- Most Arm GPUs render **16×16 pixel tiles**. Older parts have **128 bits/pixel** of tile-buffer colour storage, Mali-G72 and later up to **256 bpp**, and "recent GPUs have up to 1024 bits per pixel". Going over the budget forces smaller tiles, "which can reduce performance". Arm's advice is to keep a G-buffer at ≤128 bpp, and in any case within 256 bpp. — [Arm GPU Best Practices Developer Guide r3.4 (101897_0304_10, 2025)](https://documentation-service.arm.com/static/67a62b17091bfc3e0a947695)
- Arm guide, render-pass rules: clear or invalidate every attachment at pass start (`LOAD_OP_CLEAR`/`DONT_CARE`). Make single-pass attachments `TRANSIENT_ATTACHMENT` backed by `LAZILY_ALLOCATED` memory. Discard at the end with `STORE_OP_DONT_CARE`. "Do not use loadOp = LOAD_OP_LOAD unless your algorithm relies on the initial framebuffer state." — [Arm GPU Best Practices r3.4](https://documentation-service.arm.com/static/67a62b17091bfc3e0a947695)
- Transaction Elimination works on 16×16 tiles. It skips writing tiles whose CRC matches the previous frame. The Khronos sample measured "~10% reduction in write bandwidth" with correct layouts. Using `TRANSIENT_ATTACHMENT` disables it for that image. — [Khronos Vulkan-Samples, layout_transitions](https://github.com/KhronosGroup/Vulkan-Samples/tree/main/samples/performance/layout_transitions)
- AFBC (lossless framebuffer compression) cuts system bandwidth for image data "by up to 50%". **Storage images cannot use AFBC.** `imageLoad`/`imageStore` on a framebuffer attachment triggers decompression. — [azhirnov/cpu-gpu-arch, ARM-Mali guide (third-party digest of Arm docs)](https://github.com/azhirnov/cpu-gpu-arch/blob/main/gpu/ARM-Mali_Guide.md)

**Measured on Mali-G76 (Khronos / Samsung)**
- Khronos subpasses sample on a Galaxy S10 with Mali-G76 at 2220×1080: merging G-buffer and lighting into subpasses gave "approximately a 55% reduction in the number of tiles used (262.2k/s vs 614.7k/s), and therefore a 55% reduction in bandwidth". — [Khronos Vulkan-Samples, subpasses](https://github.com/KhronosGroup/Vulkan-Samples/tree/main/samples/performance/subpasses)
- Khronos render_passes sample: `LOAD_OP_LOAD` versus `LOAD_OP_CLEAR` on the colour attachment cost **600.2 MiB/s** of extra read bandwidth. Storing an unneeded depth attachment cost **554.8 MiB/s** of writes at about 60 FPS. The sample's cost formula is `width × height × bpp/8 × FPS`. — [Khronos Vulkan-Samples, render_passes](https://github.com/KhronosGroup/Vulkan-Samples/tree/main/samples/performance/render_passes)
- Khronos MSAA sample on Mali-G76: 4× MSAA resolved in tile costs only "3% bandwidth increase". Resolving in a separate pass "consumes much more bandwidth". — [Khronos Vulkan-Samples, msaa](https://github.com/KhronosGroup/Vulkan-Samples/tree/main/samples/performance/msaa)
- Samsung (Vulkanised 2023) on a shipped game with locked sustainable clocks: subpasses gave **49 FPS at 725 mA**, separate render passes **41 FPS at 872 mA**. Switching a render target from R16G16B16A16F to **R11G11B10F** took Forza Street on a Note10 (Mali-G76, 2048×1080) from **53 to 60 FPS**. The same deck frames mobile as about 5 W, passively cooled, with shared memory at about 30 GB/s, against desktop at 300–500 W and about 300 GB/s. — [Samsung/Khronos, Battle-tested optimisations for mobile (Vulkanised 2023)](https://vulkan.org/user/pages/09.events/vulkanised-2023/vulkanised_2023_battle_tested_optimisations_for_mobile_v2.pdf)
- Samsung's load-op ranking: `DONT_CARE` is fastest. `CLEAR` is "fast on TBDRs, slower on Xclipse (IMR)", and should be preferred over shader clears. `LOAD` is "slowest option". — [Samsung, Vulkanised 2023](https://vulkan.org/user/pages/09.events/vulkanised-2023/vulkanised_2023_battle_tested_optimisations_for_mobile_v2.pdf)

**Qualcomm Adreno**
- Adreno is tile-based ("binning"). A binning pass records which bins each primitive touches, and each bin is then rendered into on-chip **GMEM**. **FlexRender** lets the driver pick per render target between binned/GMEM mode and direct rendering to system memory. Qualcomm's guide says the choice can change mid-frame, so developers should optimise for both modes. — [Qualcomm Game Developer Guide, Adreno mobile best practices](https://docs.qualcomm.com/bundle/publicresource/topics/80-78185-2/mobile_best_practices.html); [Meta, Advanced GPU pipelines, loads, stores and passes](https://developers.meta.com/vr/documentation/native/android/po-advanced-gpu-pipelines/)
- Qualcomm's best-practice list: maximise UBWC (bandwidth compression); optimise manually for GMEM; reduce render-pass boundaries, barriers and depth clears that block concurrent binning; prefer Vulkan over GLES. — [Qualcomm Adreno best practices](https://docs.qualcomm.com/bundle/publicresource/topics/80-78185-2/mobile_best_practices.html)
- GMEM size by chip: 512 kB on QCS5430/QCS6490/QCS8275, 1.5 MB on QCS9075 (Qualcomm Linux table). A third-party review reports 3 MB of GMEM with ">2 TB/s" on Adreno X1 (Snapdragon X, a laptop part). — [Qualcomm Linux graphics overview](https://docs.qualcomm.com/doc/80-70022-19/topic/graphics-overview.html); [HotHardware](https://hothardware.com/reviews/snapdragon-x-oryon-cpu-and-adreno-gpu-architecture?page=2)
- Direct rendering disables LRZ (low-resolution Z early reject). Third-party guide: on Adreno, RGB10_A2 is faster than FP16. — [azhirnov, Adreno guide](https://github.com/azhirnov/cpu-gpu-arch/blob/main/gpu/Adreno_Guide.md)
- A measured, old figure: about 14–15 GB/s achieved DRAM bandwidth on Adreno 530 (Snapdragon 820, 2016), against 29.8 GB/s theoretical. — [Chips and Cheese, Inside Adreno 530](https://chipsandcheese.com/p/inside-qualcomms-adreno-530-a-small-mobile-igpu)

### Inferences
- **[derived]** Per full-screen write at 1080p (2,073,600 px): RGBA8 = 8.3 MB, RG11B10 = 8.3 MB, RGBA16F = 16.6 MB. At 1440p (2560×1440 = 3.69 Mpx) RGBA16F = 29.5 MB. One RGBA16F light buffer written once and read once per frame at 1080p is 33 MB/frame: **2.0 GB/s at 60 Hz, 4.0 GB/s at 120 Hz**. By Arm's 100 mW/(GB/s) rule that is about **0.2 W and 0.4 W**, i.e. 4–8 % of a 5 W SoC budget for one buffer round trip. At 1440p/120 Hz the same round trip is about 7 GB/s, roughly 0.7 W.
- **[derived]** Against an achieved DRAM bandwidth of 15–30 GB/s, one RGBA16F read+write at 1080p costs at least about 1.1–2.2 ms of pure memory time if nothing overlaps it. An 8.3 ms frame at 120 Hz can afford very few such passes.
- Design implication: a 2D lighting system that beats Godot on mobile should minimise **materialised** full-screen intermediates (normal buffer, light buffer, SDF, cascades). Use the smallest formats that work (RG11B10/RGB10A2 or R16 instead of RGBA16F). Run light-only buffers at reduced resolution. Fold cheap steps (tonemap, composite, recolour) into the final pass rather than adding passes.
- Additive blending of many light quads **inside one render pass** is cheap on a TBDR, because blending happens in tile memory. Each extra pass boundary is what costs.

### Gaps
- No official Imagination/PowerVR document with numbers was retrieved.
- Qualcomm's own bandwidth-savings numbers (the "Bandwidth Optimization" and "Bin Minimization" pages) were not retrieved.
- The Arm 100 mW/(GB/s) figure is undated and not tied to a DRAM generation. LPDDR5X is likely lower per bit; I found no source.

## 2. Framebuffer fetch, programmable blending, subpasses, imageblocks/tile shaders, raster order groups: what they give, and what wgpu exposes

### Takeaway
On-tile techniques (framebuffer fetch, subpass input attachments, Metal imageblocks, tile shaders and raster order groups) would let G-buffer, normals and light accumulation for a 2D deferred lighting pass stay entirely in tile memory. **None of them is exposed by wgpu 29 or 30.** What wgpu does expose: transient (memoryless / lazily-allocated) attachments since **v28** (`TextureUsages::TRANSIENT`, PR #8247), `LoadOp::DontCare` since **v28** (PR #8549), and normal `LoadOp::Clear` / `StoreOp::Discard`. A transient attachment cannot be sampled in a later pass, and wgpu has no input attachments. So in wgpu 29, transient textures help only with MSAA colour and depth/stencil that are never read back. They cannot keep a normal buffer or light buffer on-tile.

### Cited findings
**What the hardware/APIs offer**
- Apple: imageblocks are "tiles of structured image data stored in local memory". They persist "for the lifetime of a tile, across draws and dispatches", and both fragment and kernel functions can use them. Tile shaders "combine rendering and compute operations into a single render pass while sharing local memory". Raster order groups make overlapping fragments' read-modify-write happen in submission order. Multiple order groups let deferred shading "coalesce both render phases into one". These features arrived with A11 and later. — [Apple TBDR doc](https://developer.apple.com/documentation/metal/tailor-your-apps-for-apple-gpus-and-tile-based-deferred-rendering)
- Arm: Mali can use colour and depth attachments of one subpass as input attachments in a later subpass "without going through the main memory". That enables deferred shading and programmable blending, within the 128/256/1024 bpp tile budget and using `DEPENDENCY_BY_REGION_BIT`. — [Arm GPU Best Practices r3.4](https://documentation-service.arm.com/static/67a62b17091bfc3e0a947695)
- Arm on Vulkan framebuffer fetch: vanilla subpasses need a barrier between each colour write and the matching input-attachment read. That "makes techniques such as programmable blending difficult … because you cannot insert these barriers between primitives in the same draw call". New Vulkan apps prefer Dynamic Rendering, which has one subpass per pass. — [Arm blog, Framebuffer fetch in Vulkan](https://developer.arm.com/community/arm-community-blogs/b/mobile-graphics-and-gaming-blog/posts/framebuffer-fetch-in-vulkan)
- Adreno: a subpass self-dependency defaults to **non-coherent** mode in the Vulkan driver, because the spec does not require ordering. A developer saw wrong pixels on one Adreno chip and not on another. — [Qualcomm developer forum](https://developer.qualcomm.com/comment/20928)
- Meta/Qualcomm: subpass merging only applies when the surface is rendered in binning mode. In direct mode (FlexRender), the on-tile benefit disappears. — [Meta developer docs](https://developers.meta.com/vr/documentation/native/android/po-advanced-gpu-pipelines/)

**WebGPU / Dawn**
- Dawn (Chrome) has an **experimental** WGSL extension, `chromium_experimental_framebuffer_fetch` (`@color(N)` fragment inputs), on tiler Metal GPUs and on Vulkan with `InputAttachment`. Dawn's docs say WebGPU specification work had not started. — [Dawn docs, chromium_experimental_framebuffer_fetch](https://dawn.googlesource.com/dawn/+/main/docs/tint/extensions/chromium_experimental_framebuffer_fetch.md)
- The WebGPU spec (W3C CRD, 15 Sep 2026) defines `GPUTextureUsage.TRANSIENT_ATTACHMENT` (0x20): "The texture is intended to be temporary (a hint for optimization), as it is only used within a render pass". It must be exactly `TRANSIENT_ATTACHMENT | RENDER_ATTACHMENT`. — [W3C WebGPU CRD 2026-09-15](https://www.w3.org/TR/webgpu/); [gpuweb proposal: transient-attachments](https://github.com/gpuweb/gpuweb/blob/main/proposals/transient-attachments.md)

**wgpu (each claim tied to a version or PR)**
- **v28.0.0 (2025-12-17)**: "Added support for transient textures on Vulkan and Metal" — PR [#8247](https://github.com/gfx-rs/wgpu/pull/8247), merged 2025-10-16. It "Exposes `MTLStorageMode.memoryless` for Metal and `vk::MemoryPropertyFlags::LAZILY_ALLOCATED` for Vulkan by adding `TextureUsages::TRANSIENT`". In v29.0.0 source, `TRANSIENT` "Requires `StoreOp::Discard`". v28.0.1 re-added support on Apple A7 ([#8725](https://github.com/gfx-rs/wgpu/pull/8725)). — [wgpu CHANGELOG](https://github.com/gfx-rs/wgpu/blob/trunk/CHANGELOG.md); [wgpu-types v29.0.0 texture.rs](https://github.com/gfx-rs/wgpu/blob/v29.0.0/wgpu-types/src/texture.rs)
- **v28.0.0**: new `LoadOp::DontCare` (requires an `unsafe` token `LoadOpDontCare::enabled()`; falls back to another load op where unsupported) — PR [#8549](https://github.com/gfx-rs/wgpu/pull/8549). v30 made it non-deserialisable ([#9428](https://github.com/gfx-rs/wgpu/pull/9428)). — [wgpu CHANGELOG](https://github.com/gfx-rs/wgpu/blob/trunk/CHANGELOG.md)

- **Input attachments / subpasses: not implemented.** Issue [#10148](https://github.com/gfx-rs/wgpu/issues/10148), "RenderPipeline input attachments", was opened 2026-08-22 and is still open. The naga side, [#5233](https://github.com/gfx-rs/wgpu/issues/5233) "naga: Input attachments" (opened 2024-02-10), is also open. — [wgpu #10148](https://github.com/gfx-rs/wgpu/issues/10148); [wgpu #5233](https://github.com/gfx-rs/wgpu/issues/5233)
- A GitHub search of gfx-rs/wgpu for "framebuffer fetch", "pixel local storage" and "tile shader" found **no** feature issue or PR, only unrelated GLES bug reports. No raster-order-group, imageblock or tile-shader feature exists in the v29 `features.rs`. — searched 2026-10-08 via GitHub API; [wgpu-types v29.0.0 features.rs](https://github.com/gfx-rs/wgpu/blob/v29.0.0/wgpu-types/src/features.rs)
- Related: `DUAL_SOURCE_BLENDING` is a WebGPU-compliant feature (moved to spec syntax earlier; SPIR-V support in v29, [#8865](https://github.com/gfx-rs/wgpu/pull/8865)). It is the only extended-blend capability. — [wgpu CHANGELOG](https://github.com/gfx-rs/wgpu/blob/trunk/CHANGELOG.md)

### Inferences
- With wgpu 29, a 2D deferred design (normal/albedo buffer, then light pass) **must** store the normal buffer to DRAM and sample it in the next pass. There is no on-tile path, so its cost is exactly the round-trip bandwidth computed in §1.
- The on-tile-friendly design reachable today is **forward per-sprite lighting**: each sprite's fragment shader loops over a culled light list or samples a light texture. Alternatively, draw all light quads additively into one light-accumulation attachment in one pass (blending stays on-tile), store it once, and sample it once in the composite. The second option costs one store plus one read of the light buffer, and nothing else.
- `TRANSIENT` (v28/v29) is worth using for the depth/stencil of the sprite pass and any MSAA colour target (lazily-allocated or memoryless memory saves RAM). Expect no bandwidth gain beyond what `StoreOp::Discard` already gives.
- Native-only escape hatches exist outside wgpu's safe API (raw Metal/Vulkan via `wgpu-hal` interop). They would break WebGPU/GLES parity and are not "reachable from wgpu" in the portable sense.

### Gaps
- I did not confirm whether wgpu's GLES backend maps `TRANSIENT` to anything. PR #8247 names only Vulkan and Metal.
- No measured numbers for Apple imageblock/ROG deferred lighting versus multi-pass.

## 3. Compute on mobile: cost versus fragment, workgroup sizes, storage-texture formats, f16

### Takeaway
On Mali, Arm's guidance is to **use fragment shaders for simple image processing**. Fragment passes get fixed-function interpolation, tile write-back in parallel with shading, AFBC and transaction elimination. Compute storage writes lose AFBC, and FRAGMENT→COMPUTE→FRAGMENT dependencies create pipeline bubbles. Compute wins when threads share data (shared memory) or when it merges many fragment passes into one dispatch, as with FFT, or plausibly JFA levels and radiance-cascade merges. Mali "shared memory" is **not on-chip**: it is system RAM behind the load/store cache. Use 64-thread (8×8) workgroups. In WebGPU and wgpu, `rgba16float` storage is write-only or read-only in core. `r16float` storage needs `texture-formats-tier1`, which wgpu has **not implemented** (#8122 open). Read-write needs tier 2, or the wgpu-native `TEXTURE_ADAPTER_SPECIFIC_FORMAT_FEATURES`. `SHADER_F16` works on Vulkan, Metal, DX12 and WebGPU but not GLES.

### Cited findings
**Compute versus fragment**
- Arm guide §9.1: "fragment shaders have access to many fixed-function features … can speed up performance, reduce power, and even reduce bandwidth. Ideally, use fragment shaders for image processing where possible." Fragment advantages: fixed-function varying interpolation; "write out to memory using the tile-writeback hardware in parallel to the shader code"; no `imageStore` range checks; "framebuffer compression and transaction elimination". Compute advantages: shared data between neighbouring pixels; larger working sets; algorithms "which require multiple fragment render passes … often possible to merge into a single compute dispatch". Arm's guidance: "Use fragment shaders for simple image processing." — [Arm GPU Best Practices r3.4](https://documentation-service.arm.com/static/67a62b17091bfc3e0a947695)
- Arm guide §9.3: "Arm GPUs do not implement dedicated on-chip shared memory for compute shaders. The shared memory … is system RAM that is backed up by the load-store cache." Keep it small and reduce precision and data widths. — [Arm GPU Best Practices r3.4](https://documentation-service.arm.com/static/67a62b17091bfc3e0a947695)
- Arm's guidance names pipeline bubbles and says to "avoid FRAGMENT -> COMPUTE workloads due to the bubbles which will inevitably follow". Measured bloom on a Galaxy S9 (Exynos, Mali; clocks held equal), 2018: fragment **21.5 ms**, compute on the same queue **19.8 ms**, async compute on two queues **19.4 ms**. The author found compute faster than expected and suspected cache maintenance between back-to-back render passes. Compute on the swapchain loses "framebuffer compression and transactional elimination". — [Arm blog (H.-K. Arntzen), Using compute post-processing in Vulkan on Mali, 2018-06-13](https://developer.arm.com/community/arm-community-blogs/b/mobile-graphics-and-gaming-blog/posts/using-compute-post-processing-in-vulkan-on-mali)

**Workgroup / subgroup sizes**
- Arm: "Use 64 as a baseline workgroup size. Use a multiple of 4 … Try smaller workgroup sizes before larger ones, especially if using barriers or shared memory … use a square execution dimension, for example 8x8". With barriers or shared memory the GPU cannot split workgroups, which raises register pressure and can spill to stack. — [Arm Best Practices, Workgroup sizes](https://developer.arm.com/documentation/101897/0304/Compute-shading/Workgroup-sizes)
- Mali warp width: Valhall uses 16 lanes, Mali-G52/G76 8, early Bifrost 4. "Arm GPUs currently use subgroup sizes of 16 and smaller". Valhall: 0–32 registers per thread keeps maximum warps per core. — [azhirnov Mali guide](https://github.com/azhirnov/cpu-gpu-arch/blob/main/gpu/ARM-Mali_Guide.md); [Arm Mali-G310 counters guide](https://developer.arm.com/documentation/102810/0110/Shader-core-data-path)
- A 2019 study found Mali performance "robust … independent of configured work group sizes", with tuning gains usually under 5 %. — [arXiv 1907.01989, On-device NN inference with mobile GPUs](https://arxiv.org/pdf/1907.01989)
- wgpu: `Features::SUBGROUP` (compute and fragment) on Vulkan, DX12 and Metal. It stays native-only even though WebGPU added `subgroups`, because of differences tracked in [#5555](https://github.com/gfx-rs/wgpu/issues/5555). Since v28, subgroup min/max sizes live in `AdapterInfo`. — [wgpu-types v29.0.0 features.rs](https://github.com/gfx-rs/wgpu/blob/v29.0.0/wgpu-types/src/features.rs); [wgpu CHANGELOG](https://github.com/gfx-rs/wgpu/blob/trunk/CHANGELOG.md)

**Storage-texture formats (WebGPU spec, CRD 2026-09-15)**
- Core: `rgba16float` storage is "write-only" and "read-only". "read-write" needs `texture-formats-tier2`. `r32float` has read-write in core (also `r32uint`/`r32sint`). — [W3C WebGPU §26.1.1](https://www.w3.org/TR/webgpu/)
- `texture-formats-tier1` adds read-only and write-only storage for `r8unorm`, `r8snorm`, `rg8*`, `r16uint`, `r16sint`, **`r16float`**, `rg16uint`, `rg16sint`, **`rg16float`**, **`rgb10a2unorm`**, **`rg11b10ufloat`**, and others. It also adds `r16unorm`-family formats with render, blend and storage support. — [W3C WebGPU §25.19](https://www.w3.org/TR/webgpu/)
- `texture-formats-tier2` adds **read-write** for `r8unorm`, `r8uint`, `r8sint`, `rgba8unorm`, `rgba8uint`, `rgba8sint`, `r16uint`, `r16sint`, **`r16float`**, `rgba16uint`, `rgba16sint`, **`rgba16float`**, `rgba32*`. — [W3C WebGPU §25.20](https://www.w3.org/TR/webgpu/)
- wgpu has **not** implemented tier 1 or tier 2. Issue [#8122](https://github.com/gfx-rs/wgpu/issues/8122) (opened 2025-08-19) is still open; a 2026-01-28 maintainer comment says only a WIP commit exists, "PRs welcome". The WGSL `texture_formats_tier1` language extension, [#8962](https://github.com/gfx-rs/wgpu/issues/8962), is also open. Firefox (which uses wgpu) therefore lacks `texture-formats-tier1`. — [wgpu #8122](https://github.com/gfx-rs/wgpu/issues/8122); [wgpu #8962](https://github.com/gfx-rs/wgpu/issues/8962)
- wgpu-native: `TEXTURE_ADAPTER_SPECIFIC_FORMAT_FEATURES` "extends the features of each format to the ones supported by the current device. Note that without this flag, read/write storage access is not allowed at all." That doc comment predates the core `r32float` read-write rule. Storage access modes `ReadOnly`/`ReadWrite` exist since v0.20 ([#5434](https://github.com/gfx-rs/wgpu/pull/5434)). The `readonly_and_readwrite_storage_textures` WGSL extension was marked implemented in v26 ([#7543](https://github.com/gfx-rs/wgpu/pull/7543)). `TEXTURE_FORMAT_16BIT_NORM` (native) is on Vulkan, DX12 and Metal, and on GL since v30 ([#9601](https://github.com/gfx-rs/wgpu/pull/9601)). — [wgpu-types v29 features.rs](https://github.com/gfx-rs/wgpu/blob/v29.0.0/wgpu-types/src/features.rs); [wgpu CHANGELOG](https://github.com/gfx-rs/wgpu/blob/trunk/CHANGELOG.md)
- `FLOAT32_BLENDABLE` was added on Vulkan and Metal in v29.0.0 ([#8963](https://github.com/gfx-rs/wgpu/pull/8963), [#9032](https://github.com/gfx-rs/wgpu/pull/9032)). `BGRA8UNORM_STORAGE` is on Vulkan, DX12, Metal and WebGPU. — [wgpu CHANGELOG](https://github.com/gfx-rs/wgpu/blob/trunk/CHANGELOG.md)

**Half precision (f16)**
- wgpu `Features::SHADER_F16`, v29: "Supported Platforms: Vulkan, Metal, DX12, WebGPU". It is a web and native feature, enabled in WGSL with `enable f16;`, and f16 is not allowed in immediates. — [wgpu-types v29.0.0 features.rs](https://github.com/gfx-rs/wgpu/blob/v29.0.0/wgpu-types/src/features.rs)
- History: in v25.0.0 (2025-04-10), `SHADER_F16` became usable from naga (WGSL/GLSL/SPIR-V) instead of SPIR-V passthrough only. In v27.0.0, an f16 IO polyfill on Vulkan removed the need for `storageInputOutput16` ([#7884](https://github.com/gfx-rs/wgpu/pull/7884)), which matters on mobile Vulkan drivers that lack it. In v29.0.0, f16 constants were fixed ([#8816](https://github.com/gfx-rs/wgpu/pull/8816)). In v30.0.0, naga forbids derivatives on f16 ([#9154](https://github.com/gfx-rs/wgpu/pull/9154); WGSL issue [gpuweb#5482](https://github.com/gpuweb/gpuweb/issues/5482)). — [wgpu CHANGELOG](https://github.com/gfx-rs/wgpu/blob/trunk/CHANGELOG.md)
- Arm: "Arm GPUs have full support for reduced precision in the shader core register file and arithmetic units … Using 16-bit precision is normally sufficient … for fragment shading when computing an output color". 16-bit storage cuts bandwidth, and 16-bit arithmetic raises throughput. `lowp` is identical to `mediump` on Arm. — [Arm GPU Best Practices r3.4 §10.1](https://documentation-service.arm.com/static/67a62b17091bfc3e0a947695)
- Mali: use vectorised `f16vec2`/`f16vec4`, because scalar `float16_t` misses the packed f16×2 gain. Also on Mali: "Do not blend on floating-point framebuffers", and prefer unorm formats for blending. This is a third-party digest of Arm guidance. — [azhirnov Mali guide](https://github.com/azhirnov/cpu-gpu-arch/blob/main/gpu/ARM-Mali_Guide.md)
- Adreno: FP16 inverse square root is about 2× faster than FP32 (no device named). — [azhirnov Adreno guide](https://github.com/azhirnov/cpu-gpu-arch/blob/main/gpu/Adreno_Guide.md)
- Apple: the register file is built from 16-bit registers, so 32-bit values take two slots and f16 doubles effective register capacity. That is an occupancy gain, not necessarily an ALU-rate gain. — [RealWorldTech, A look inside Apple's custom GPU](https://www.realworldtech.com/apple-custom-gpu/); [Apple developer forum thread 706625](https://developer.apple.com/forums/thread/706625). On M1 (reverse-engineered), occupancy is 1024 threads at ≤104 registers, falling to 384 threads at 240–256. — [Rosenzweig, Dissecting the Apple M1 GPU part III](https://rosenzweig.io/blog/asahi-gpu-part-3.html)
- Samsung warns that compilers may promote precision. Mismatched mediump/highp operands promote to highp; test on many devices. — [Samsung, Vulkanised 2023](https://vulkan.org/user/pages/09.events/vulkanised-2023/vulkanised_2023_battle_tested_optimisations_for_mobile_v2.pdf)

### Inferences
- **JFA / SDF cost [derived]**: a full-resolution JFA at 1080p has about 11 passes (log2 2048). With 4 B/px seeds (`rg16uint`), each pass writes ≥8.3 MB and reads ≥8.3 MB, about 180 MB per frame. That is about 11 GB/s at 60 Hz, roughly 1.1 W by Arm's rule, and it sits at the order of the whole achieved DRAM bandwidth on older Adreno. At half resolution it drops about 4×. At 1/4 resolution it is about 0.7 GB/s.
  - So the SDF should be built at reduced resolution and/or only in dirty regions.
  - Use the narrowest seed format. `rg16uint` is core-storage in WebGPU (write-only/read-only); `r32uint` packing gives read-write in core.
- For iterative compute in wgpu 29 that needs **read-write on the same texture**, the portable choices are `r32float`, `r32uint` and `r32sint` (core read-write). Otherwise use ping-pong between two textures, write-only on one and read via `textureLoad`/sampling on the other. `rgba16float` read-write is native-only through `TEXTURE_ADAPTER_SPECIFIC_FORMAT_FEATURES`, and unavailable on the web through wgpu until #8122 lands.
- A light-accumulation buffer filled by **additive blending of light quads in a fragment pass** fits mobile hardware better than a compute scatter: on-tile blending, AFBC/UBWC on the store, no bubbles. That holds for Mali at least. The "don't blend on float framebuffers" note argues for RGB10A2 or a scaled `rgba8unorm`/`rg11b10ufloat` light buffer, or HDR via a scale factor, rather than RGBA16F blending, on Mali and Adreno. This needs measuring.
- Radiance-cascade merges (many small dependent passes) are the case where Arm says compute can win, by merging passes in one dispatch. Even so, workgroup shared memory on Mali is not on-chip, so cascade data should stay small (f16 / packed).

### Gaps
- No vendor-official per-format storage-texture support matrix for mobile Vulkan drivers (e.g. which Mali/Adreno drivers allow `rgba16float` read-write) was retrieved. Check gpuinfo.org per device.
- No measured f16-versus-f32 speedups for a lighting-type shader on named Mali/Adreno/Apple GPUs. The Khronos `16bit_arithmetic` sample exists, but its README gives no number.
- Adreno wave size (64/128) and workgroup guidance from Qualcomm were not retrieved from a primary source.

## 4. Reduced-resolution lighting and upsampling (bilateral, depth/normal-aware, checkerboard, temporal)

### Takeaway
The vendor material supports rendering expensive passes at reduced resolution and upscaling with a textured full-screen quad, only when fragment-bound. Joint bilateral upsampling (Kopf et al. 2007) is the standard edge-preserving method. In 2D lighting the guide can be the full-resolution normal/albedo or the occluder SDF. I found no mobile-specific measurements of bilateral or temporal upsampling cost for 2D lighting.

### Cited findings
- Samsung (Vulkanised 2023): render a pass at lower resolution (e.g. 480p) and upscale to 720p in a subpass before a full-resolution UI pass, "Only when limited by fragment shading throughput!". "Prefer textured full-screen quad upscale over vkCmdBlitImage", and consider AMD FSR. They demonstrated it on Adreno 740 and Xclipse 920 (483p→720p + RCAS). — [Samsung/Khronos, Vulkanised 2023](https://vulkan.org/user/pages/09.events/vulkanised-2023/vulkanised_2023_battle_tested_optimisations_for_mobile_v2.pdf)
- Joint bilateral upsampling: a low-resolution solution is upsampled using a full-resolution guide image as a prior, which avoids the edge smearing of smooth interpolators. The original applications were exposure/tone-mapping maps and stereo depth. — [Kopf, Cohen, Lischinski, Uyttendaele, Joint Bilateral Upsampling, SIGGRAPH 2007](https://johanneskopf.de/publications/jbu/paper/FinalPaper_0185.pdf)
- A 2025 Chalmers master's thesis studies 2D screen-space Radiance Cascades and "presents comparative analysis between different upscaling techniques" (not read in full). — [Chalmers ODR thesis](https://odr.chalmers.se/bitstreams/256da4eb-990c-4e51-aae1-c7878609e314/download)
- Godot 4: "Lighting and shadows are computed at the viewport's pixel resolution", not texel resolution, so window size drives cost. — [Godot docs, 2D lights and shadows](https://docs.godotengine.org/en/stable/tutorials/2d/2d_lights_and_shadows.html)

### Inferences
- **[derived]** At half resolution in each axis, a light buffer has ¼ the pixels: RGBA16F at 1080p falls from 16.6 MB to 4.1 MB per write. A joint-bilateral upsample folded into the **final composite pass** (reading 4 low-res taps plus the full-resolution normal/albedo already being read) adds ALU work but no extra full-screen pass. That keeps the pass count at "light buffer store + one composite read".
- 2D-specific artefacts to expect: light leaking across sprite silhouettes and occluder edges at low resolution, which is what a guided/bilateral weight on the occluder mask or SDF fixes, and shimmering of hard shadow edges under camera movement. Temporal accumulation in 2D can reproject using only camera pan/zoom (no depth). Moving sprites and lights still need disocclusion/rejection, or they ghost. These are reasoned expectations; I found no sourced measurements.
- Since Godot computes lighting at full viewport resolution, a reduced-resolution light buffer with an edge-aware upsample is a straightforward way to undercut its per-pixel cost on mobile while keeping sprite edges sharp.

### Gaps
- No sourced per-ms cost of a bilateral upsample or a TAA resolve on a named mobile GPU.
- No sourced study of temporal-accumulation artefacts in 2D lighting specifically.
- Checkerboard rendering on mobile: no source found.

## 5. Real measured numbers: per-pass cost, bandwidth, thermal throttling

### Takeaway
Published per-pass millisecond figures for named mobile GPUs at 1080p/1440p are scarce. The best measured data points are the Mali-G76 bandwidth/tile counts (Khronos, Samsung), the S9 bloom timings (Arm) and a 14–15 GB/s achieved DRAM bandwidth on Adreno 530. Sustained-performance tests show flagship phones losing roughly **33–56 %** of peak GPU performance under sustained load. A 60/120 Hz lighting budget therefore has to be planned against throttled clocks, not peak.

### Cited findings
- Mali-G76 (S10, 2220×1080, 16×16 tiles): about 9k tiles per frame, so about 270k tiles/s at 30 FPS. Subpasses cut tiles and bandwidth by about 55 %. — [Khronos subpasses sample](https://github.com/KhronosGroup/Vulkan-Samples/tree/main/samples/performance/subpasses)
- Mali-G76: 600.2 MiB/s from an unnecessary colour `LOAD`; 554.8 MiB/s from an unnecessary depth `STORE` (about 60 FPS). — [Khronos render_passes sample](https://github.com/KhronosGroup/Vulkan-Samples/tree/main/samples/performance/render_passes)
- Mali (Galaxy S9 Exynos), bloom: fragment 21.5 ms, compute 19.8 ms, async compute 19.4 ms (total frame times with a bloom chain, 2018). — [Arm blog](https://developer.arm.com/community/arm-community-blogs/b/mobile-graphics-and-gaming-blog/posts/using-compute-post-processing-in-vulkan-on-mali)
- Mali-G76 (Note10, 2048×1080): RGBA16F→R11G11B10F render target, 53→60 FPS. Subpasses versus separate passes: 49 versus 41 FPS, 725 versus 872 mA. All with locked sustainable clocks. — [Samsung, Vulkanised 2023](https://vulkan.org/user/pages/09.events/vulkanised-2023/vulkanised_2023_battle_tested_optimisations_for_mobile_v2.pdf)
- Adreno 530 (Snapdragon 820): about 14–15 GB/s achieved versus 29.8 GB/s theoretical. — [Chips and Cheese](https://chipsandcheese.com/p/inside-qualcomms-adreno-530-a-small-mobile-igpu)
- Thermal, 3DMark Wild Life stress tests with active cooling off:
  - Dimensity 9300 (vivo X100 Pro, Immortalis-G720) ended at **44 % stability**.
  - Snapdragon 8 Gen 3 (REDMAGIC 9 Pro, Adreno 750) held **67 %**. On Wild Life Extreme it lost about 30 % between the first and second runs, then held.
  - [Android Authority](https://www.androidauthority.com/snapdragon-8-gen-3-dimensity-9300-benchmarked-3395385/); [Android Authority (Extreme)](https://www.androidauthority.com/snapdragon-8-gen-3-vs-dimensity-9300-benchmarked-3395385/)
- Another reviewer's retest of an SD 8 Gen 3 phone: 65.5 % Extreme stability. — [Mightygadget](https://mightygadget.co.uk/?p=683347)
- A17 Pro: about 10.6 W peak in Wild Life Extreme (peak, not stability). — [Wccftech](https://wccftech.com/3dmark-wild-life-extreme-test-dimensity-9300-beats-snapdragon-8-gen-3-and-a17-pro/amp/)
- iPhone 17 Pro Max reportedly 62.8 % stability, from a Reddit-sourced test relayed by a low-quality outlet. Treat as weak. — [PhoneWorld](https://www.phoneworld.com.pk/smartphone-thermal-throttling-crisis-iphone-17-pro-max-cooling-wall-2026/)
- Samsung's methodology: "All measurements are produced using locked, sustainable frequencies". — [Samsung, Vulkanised 2023](https://vulkan.org/user/pages/09.events/vulkanised-2023/vulkanised_2023_battle_tested_optimisations_for_mobile_v2.pdf)

### Inferences
- **[derived]** Bandwidth per frame for plausible 2D lighting pipelines at 1080p/60:
  - (a) Forward per-sprite lighting: about 0 extra bytes for lighting buffers.
  - (b) Full-resolution RGBA16F light buffer, store + read: 33 MB/frame = 2 GB/s.
  - (c) Option b plus a stored full-resolution RGBA8 normal buffer, store + read: +16.6 MB, so about 3 GB/s.
  - (d) Option c plus full-resolution JFA: +about 180 MB, so about 14 GB/s, which is not viable sustained on mid-range parts.
  - Halve resolution per axis and (b)–(d) fall about 4×.
- Peak-clock measurements overstate sustained headroom by 1.5–2.3×, per the stability figures above. Benchmark lighting at locked, sustainable clocks the way Samsung does, or on a device that has run for 10+ minutes.
- wgpu measurement note: timestamp queries inside passes are gated separately, to allow profiling on tilers that only support pass-boundary timestamps (`TimestampWrites` on pass descriptors). Use pass-level timestamps to time each lighting pass. — [wgpu CHANGELOG (TimestampWrites / TIMESTAMP_QUERY_INSIDE_PASSES)](https://github.com/gfx-rs/wgpu/blob/trunk/CHANGELOG.md)

### Gaps
- **No published ms-per-full-screen-pass figures were found** for A15/A17/M1, Adreno 6xx/7xx/8xx or Mali-G710/Immortalis at 1080p/1440p. They must be measured in-house.
- No A17 Pro sustained-stability figure from a comparable source.
- Achieved DRAM bandwidth for current flagships (LPDDR5X SoCs) was not found from a primary measurement.

## 6. How shipping engines budget 2D/screen lighting on mobile (Godot 4, Unity, vendor guidance)

### Takeaway
Godot 4 computes 2D lights per pixel at viewport resolution. Its docs push users toward "additive sprites" as the much cheaper alternative, and reserve expensive shadow filters for "a few lights". Vendor guidance is consistent: few render passes, clear or don't-care loads, discard stores, small formats, reduced precision, fragment shaders for simple image work, and in-tile resolve and merging. A wgpu engine can beat Godot on mobile mainly by:
- doing less work per pixel: a reduced-resolution light buffer, culled light lists, and SDF/shadow data built at low resolution or incrementally;
- not adding passes: composite, upsample and tonemap fused into the final pass, with `LoadOp::Clear`/`DontCare` and `StoreOp::Discard` everywhere possible.

### Cited findings
- Godot 4, from its docs:
  - Lights and shadows are computed at viewport pixel resolution.
  - Larger light "Texture Scale" "affect[s] more pixels on screen", which raises cost.
  - Shadow filter `None` is fastest. PCF13 is the most demanding and "should only be used for a few lights at once".
  - Additive sprites are "much faster to render" than 2D lights, but cast no shadows and ignore normal/specular maps.
  - Occluders can feed a real-time SDF ("SDF Collision") with no cost unless a custom shader reads it.
  - Light and occluder cull masks reduce work.
  - [Godot docs, 2D lights and shadows (stable)](https://docs.godotengine.org/en/stable/tutorials/2d/2d_lights_and_shadows.html)
- Arm, Samsung and Qualcomm guidance, as in §1–§3: minimise render passes and use subpasses where available; prefer `CLEAR`/`DONT_CARE` loads; never `LOAD` unless needed; discard transient attachments; use small formats (R11G11B10 over RGBA16F); use reduced precision; use fragment shaders for simple image processing. — [Arm GPU Best Practices r3.4](https://documentation-service.arm.com/static/67a62b17091bfc3e0a947695); [Samsung Vulkanised 2023](https://vulkan.org/user/pages/09.events/vulkanised-2023/vulkanised_2023_battle_tested_optimisations_for_mobile_v2.pdf); [Qualcomm Adreno best practices](https://docs.qualcomm.com/bundle/publicresource/topics/80-78185-2/mobile_best_practices.html)
- Some post-processing passes only do simple operations like recolouring, and "can be really costly" compared with folding the work into existing fragment shaders. — [Arm/Samsung SIGGRAPH 2015 mobile notes (A. Garrard)](https://community.arm.com/cfs-file/__key/communityserver-blogs-components-weblogfiles/00-00-00-20-66/siggraph2015_2D00_mmg_2D00_andrew_2D00_notes.pdf)
- "On-tile post-processing" (2026-05) argues that effects working on the current pixel or tile should stay there, and that only neighbourhood effects (bloom, DoF) should go through full-screen passes. — [thegamedev.guru, On-tile post-processing for mobile & XR (2026-05)](https://thegamedev.guru/taskforce/2026-05-on-tile-post-processing-mobile-xr/)

### Inferences
Concrete, wgpu-29-reachable plan elements that follow from the evidence:
1. Sprite pass: depth/stencil (if any) as `TRANSIENT` + `StoreOp::Discard`. Colour `LoadOp::Clear` or `DontCare` (v28+, unsafe token).
2. Light accumulation: additive light quads in a single pass into a **reduced-resolution**, small-format target (RG11B10 or RGB10A2 with scale; measure Mali float-blend cost), stored once.
3. Normals: either read the sprite normal map directly in the composite or forward pass (no G-buffer), or, if a normal buffer is unavoidable, store it at most once in RGBA8/RGB10A2.
4. Composite: one final pass that samples the light buffer with a joint-bilateral upsample and applies tonemap/grade. No separate post passes for per-pixel effects.
5. SDF/JFA and radiance cascades: low resolution, dirty-region updates, compute ping-pong with core formats (`r32*` read-write, `rgba16float` write-only), f16 maths where `SHADER_F16` exists (not GLES). Keep workgroups at 8×8 and shared memory tiny on Mali.
6. Frame budget: plan for sustained clocks (about 0.45–0.67× peak), and time each pass with pass-level timestamps.

### Gaps
- Unity's mobile 2D lighting (URP 2D Renderer) guidance and its light-texture resolution scaling were not retrieved in this pass.
- Godot 4's internal limits (lights per canvas item, per render) and its Compatibility-renderer behaviour are not in the user docs page fetched. Read the Godot source (`renderer_canvas_render_rd`, GLES3 canvas) for exact limits.
- I found no published mobile frame timings for Radiance Cascades (2D or otherwise). The TypeGPU RC runner and the `solis_2d` crate exist but publish no mobile numbers. — [TypeGPU radiance cascades](https://docs.swmansion.com/TypeGPU/ecosystem/typegpu-radiance-cascades/); [solis_2d](https://lib.rs/crates/solis_2d)
