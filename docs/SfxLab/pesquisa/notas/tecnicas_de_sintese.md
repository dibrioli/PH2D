## Which methods matter, and for which sound classes?

### Takeaway
Originality comes less from any one synthesis method than from a three-part structure: a **modelled exciter + a modal/noise resonator + a designed residual or layer**. Modal plus stochastic-event models cover the most classes at very low CPU. The best candidates for procedural work are repetitive, memory-heavy, heavily controlled or physics-driven sounds. Hero sounds (creatures, weapons) still benefit from analysis-derived hybrids rather than pure synthesis.

### Cited Findings
**Selection criteria and practice**
- Sony's Fournel lists the good candidates for procedural audio: repetitive (footsteps, impacts), large memory footprint (wind, ocean waves), needing a lot of control (car engine, creature vocalisations), highly dependent on physics (rolling ball, motion-controller sounds), and too many to design by hand (vast universes, user content) — [Fournel, SCEE, CEDEC 2010](https://cedec.cesa.or.jp/2010/archive/files/C10_P0051/C10_P0051.pdf).
- Same deck: two design approaches, bottom-up (how the sound is physically produced) and top-down (analyse examples, then find a synthesis system that emulates them). Models that "can be implemented very easily": impacts/contacts, footsteps, air/water. "Procedural audio is not necessarily more CPU expensive." Drawbacks: harder to implement and debug; lack of trained people, tools and ready-to-use models — [Fournel](https://cedec.cesa.or.jp/2010/archive/files/C10_P0051/C10_P0051.pdf).
- Fournel's conclusion: "Think asset models, not assets" — use analysis so that your own sounds become the basis for a model, instead of vendor models "limited to the idea the vendor has of the sound" — [Fournel](https://cedec.cesa.or.jp/2010/archive/files/C10_P0051/C10_P0051.pdf).
- Farnell distinguishes "shallow or phenomenal" approaches (granular, phase-vocoder resynthesis) from "essential or deep" models that capture physical behaviour. He favours open, modular toolkits over closed objects with few parameters — [Farnell interview, Designing Sound 2012](https://designingsound.org/2012/01/18/procedural-audio-interview-with-andy-farnell/).
- Farnell's 2005 proof of concept covered fire, water, wind, rain, animals, footsteps, guns and vehicles for an FPS on a 533 MHz processor, and he admits the sounds "weren't very high in quality" — [Farnell interview](https://designingsound.org/2012/01/18/procedural-audio-interview-with-andy-farnell/). Sets the honest expectation: coverage is cheap, quality is the hard part.

**Modal synthesis**
- Modal synthesis is a source-filter model: a parallel bank of first- and second-order sections, each second-order section one resonant mode. Frequency sets the pole angle, bandwidth the pole radius. The zeros are often set to zero because the ear is not very sensitive to spectral nulls — [J.O. Smith, PASP](https://ccrma.stanford.edu/~jos/pasp/Modal_Expansion.html).
- In the linear time-invariant case the modal form is generally more efficient than an explicit mass-spring-dashpot digitisation, if only audible modes are kept; nonlinear extensions may be difficult and behave unnaturally — [J.O. Smith, PASP](https://ccrma.stanford.edu/~jos/pasp/Modal_Expansion.html).
- Faust's `modeFilter` costs three multiplications per sample including gain, and is designed to avoid float precision loss at high sample rates and long decays — [Faust physmodels](https://faustlibraries.grame.fr/libs/physmodels/).
- Faust ships ready modal models: bells (up to 50 modes, 7 excitation positions, generated by `mesh2faust` from CAD), marimba bar (5 positions; sounds less like a marimba when transposed far from its ~65 Hz source), djembe (empirical parameters), interpolated modal bodies (up to 40 modes) — [Faust physmodels](https://faustlibraries.grame.fr/libs/physmodels/).

**Waveguides and Karplus-Strong**
- Karplus-Strong is a rigidly terminated ideal string with all losses lumped into one one-zero filter, excited by filling the delay line with white noise. Lowpassing the noise acts as a dynamic-level control, because struck strings are brighter when played louder — [J.O. Smith, PASP](https://ccrma.stanford.edu/~jos/pasp/Karplus_Strong_Algorithm.html).
- Faust also provides waveguide strings and tubes, bowed strings, clarinet, brass and flute models, plus FOF and formant-filter vocal synthesis — [Faust physmodels](https://faustlibraries.grame.fr/libs/physmodels/).
- Creature voices: Sony modelled the vocal tract with Kelly-Lochbaum waveguides plus a glottal oscillator. Yet the shipped EyePet vocalisations came from over a thousand animal recordings reduced to 634 waveforms driven by 95 sound scripts — [Fournel](https://cedec.cesa.or.jp/2010/archive/files/C10_P0051/C10_P0051.pdf). A real production chose the hybrid.

**Stochastic-event and particle models**
- Cook's PhISEM treats each particle collision as a decaying burst of filtered noise with exponentially decaying system energy, instead of simulating every bead; it yields a Poisson-like event distribution — [Cook, GameSoundCon 2014, seen via search extract](https://www.cs.princeton.edu/~prc/ChucKU/PerryCookPhysicalModelingGameSoundCon2014.pdf). STK's implementation exposes 23 instruments in Csound — [Csound STKShakers](https://csound.com/manual/STKShakers.html), [STK Shakers](https://ccrma.stanford.edu/software/stk/classstk_1_1Shakers.html).
- Liquids: bubble emission is the core mechanism; a single-bubble model plus a stochastic model gives streams, pouring, rivers, rain and breaking waves in real time — [van den Doel abstract](https://www.cs.ubc.ca/~kevinlb/LCI/03/vandendoel-040312.html). A bubble's impulse response is a damped sinusoid whose frequency depends on radius; statistical distributions generate streams and rain — [Fournel](https://cedec.cesa.or.jp/2010/archive/files/C10_P0051/C10_P0051.pdf).
- Footsteps: Turchet's engine splits solid from aggregate grounds; aggregate surfaces (gravel) use PhISM-family stochastic particles — [Nordahl, Serafin, Turchet, IEEE VR 2010](https://vbn.aau.dk/ws/files/40509677/NORDAHL_IEEE_VR_2010.pdf). His 2016 design principles are perceptual relevance, cartoonification, parametric temporal control and real-time use, covering foot-floor interaction, surface, shoe and walker features — [Turchet 2016](https://www.eecs.qmul.ac.uk/~josh/documents/2016/turchet%20-%202016.pdf).

**Subtractive, FM, wavetable, additive, granular**
- Wind/whoosh: Dobashi-style CFD versus noise generator plus bandpass filters is Fournel's example of bottom-up vs top-down; "classic subtractive synthesis is cheaper" for Kármán-vortex whooshes — [Fournel](https://cedec.cesa.or.jp/2010/archive/files/C10_P0051/C10_P0051.pdf). SoundSeed Air uses pure synthesis for wind and woosh (helicopter, wings, tunnel, waterfall examples) — [Audiokinetic samples](https://www.audiokinetic.com/products/wwise-add-ons/soundseed-samples).
- FM produces harmonic and inharmonic spectra, which is why it is used for metallic effects — [MusicRadar](https://www.musicradar.com/how-to/how-to-use-digital-synthesis-techniques-to-create-metallic-sounds). Chowning's bell tones let the modulation index fall with intensity, moving from complex inharmonic tones to a damped sine — [Chowning biography, Aberdeen](https://homepages.abdn.ac.uk/d.j.benson/pages/html/Chowning.html). Secondary sources; good enough for the idea only.
- sfxr-family tools: sliders shaping waveform, envelope and pitch for chiptune effects, exporting WAV — [as3sfxr listing](https://absinthe.tuxfamily.org/sdtraces/BottinHTML/Bottin_0-C_files/as3sfxr-14404.html). ZzFX: 9 controllable parameters, micro version under 500 bytes, MIT — [ZzFX README](https://github.com/KilledByAPixel/ZzFX/blob/91418012bcc12c1abb3b1141a104b71a6e5e7215/README.md).
- Granular: Csound's generator rests on Truax and Roads and exposes grain duration as a control — [Csound grain](https://csound.com/manual/opcodes/grain/). Periodically repeated grains pick up aliasing from onset timing jitter unless onsets are subsample-precise — [CCRMA note](https://ccrma.stanford.edu/~berlach/220c/granular.html).
- Sound textures: the survey lists subtractive/additive, granular, corpus-based concatenative, wavelets and physical modelling as the underlying families — [Schwarz, DAFx 2011 state of the art](https://dafx.de/paper-archive/details/61SplddyWP6RcOOx0SEdAw). McDermott and Simoncelli: textures with equal auditory statistics should sound the same — [McDermott/Simoncelli line, via PMC](https://pmc.ncbi.nlm.nih.gov/articles/PMC4143345). Newest found: TexEnv, a lightweight differentiable texture synthesiser, and TexStat as a metric — [DAFx25 paper 14](https://dafx25.dii.univpm.it/wp-content/uploads/2025/07/DAFx25_paper_14.pdf).

**Spectral processing**
- The phase vocoder treats the filter bank as a sliding short-time Fourier transform, with each channel holding instantaneous amplitude and phase; only one sinusoid should fall in each channel. It became the analysis framework for additive/sinusoidal modelling — [J.O. Smith, SASP](https://ccrma.stanford.edu/~jos/sasp/Phase_Vocoder.html).
- Its signature defect is "phasiness" (muffled, reverberant), addressed by periodically resetting phases in PVSOLA — [Moinet & Dutoit, DAFx-11](https://dafx.de/paper-archive/details/9UQ9PWY6URdHRFgtlSGduA).
- Cross-synthesis: whiten the first sound's spectral envelope, then filter it with the second's — [DAFX book, §8.3](https://www.safaribooksonline.com/library/view/dafx-digital-audio/9780470665992/c08_level1_3.xhtml).
- Spectral freeze as repeated resynthesis of one frame appears only as anecdote; summing two freeze frames' bins and phase differences reportedly failed — [comp.dsp thread](https://www.dsprelated.com/showthread/comp.dsp/368343-1.php).

### Inferences
- **Ranking (my engineering judgement, informed by the above; not a published ranking).** Value = range of original results a designer can reach.

| Rank | Method | Expressive value | Difficulty | CPU | Best for | Weak for |
|---|---|---|---|---|---|---|
| 1 | Modal + exciter + noise residual | Very high | Medium | Very low | Impacts, metal, glass, wood, UI, bells | Sustained noise, voices |
| 2 | Filtered noise + stochastic events (PhISEM, bubbles) | High | Low–medium | Very low | Fire, rain, water, gravel steps, debris, wind, whoosh | Pitched tones |
| 3 | Layering/modulation graph over the above | Very high | Low | Sum of parts | Weapons, magic, hero sounds | None; it is the assembler |
| 4 | FM/PM | High | Medium (unintuitive) | Low | Magic, sci-fi, UI, metallic, engine harmonics | Natural textures |
| 5 | Granular on own material | High | Low–medium | Medium | Magic, drones, textures, morphs, creature beds | Sharp transients |
| 6 | Spectral (freeze, cross-synthesis, convolution) | Very high for strangeness | Medium | Medium–high; offline fine | Magic, creature hybrids, tails | Runtime on many voices |
| 7 | Waveguide / Karplus-Strong | Medium–high | Medium | Very low | Strings, tubes, resonant whips, vocal tracts | Non-harmonic bodies |
| 8 | Wavetable | Medium | Low | Low | Engines, UI, drones | Physical plausibility |
| 9 | Additive | Medium | High (many controls) | Medium–high | Spectral painting backend, tonal resynthesis | Noise |

- **Class → recipe (judgement).** Impacts: Hertz-shaped exciter + modal + filtered noise click. UI: short modal or FM with a pitch envelope, 1–8 modes. Magic: FM/granular with spectral tail and physics-driven modulation. Weapons: 3–4 layers (transient click, modal body, noise tail, low thump) with per-layer variation. Creatures: glottal source + formants/waveguide tract, cross-synthesised with animal material. Footsteps: heel/toe event scheduling + solid modal or aggregate particles. Engines: RPM-locked pulse train through resonant bodies, plus noise tied to load. Wind: noise + bandpass with slow random modulation. Fire: crackle events + filtered low rumble. Water: bubble populations + filtered noise.
- Because a 32-mode voice takes about 0.07 % of this core, CPU is not what limits modal count on desktop. Mobile headroom, parameter smoothing, and denormals are more likely limits, and should be measured.
- A pure-synthesis "preset generator" will sound like sfxr-style sameness. The originality lever is exposing exciter design, layer modulation and user-supplied material as first-class ingredients. Fournel's "asset models" point suggests the same.

## How do synthesised impacts driven by physical parameters work?

### Takeaway
The working model is `sound = contact force * modal impulse response + noise + room`. Velocity and hardness set the contact time and thus brightness; material sets decay; size and shape set the frequencies. Games have shipped it (Crackdown 2 with a residual), and differentiable versions now fit modes from uncontrolled recordings, which is useful offline to build material libraries.

### Cited Findings
- DiffImpact decomposes an impact into: (1) impact force over time, (2) the "acceleration sound" click from the striker's deceleration, (3) impulse responses of struck and striking objects, (4) noise, (5) room response — [Clarke et al., CoRL 2021](https://par.nsf.gov/servlets/purl/10341944).
- Contact: a Hertz half-sine model between frictionless spheres, with a Gaussian approximation `C(t) = exp(6/τ² · (t − t_i − τ/2)²)` as printed in the extracted text (the extraction drops signs, so check the PDF; a decaying Gaussian needs a negative exponent). τ depends on velocity and material: "sharper and faster contact points as well as harder materials" reduce τ; softer, slower, duller raise it. Multiple contacts are a weighted sum — [DiffImpact](https://par.nsf.gov/servlets/purl/10341944).
- Object: `IR(t) = Σ g_k · exp(−d_k t) · sin(2π f_k t)` over the K most salient modes. They simplify by fixing gains across the body, while acknowledging that gains really vary with strike location — [DiffImpact](https://par.nsf.gov/servlets/purl/10341944). Noise is static filtered noise; reverberation is exponentially decaying filtered noise — same source.
- DiffImpact results: outperforms model-based and model-free baselines rendering held-out impacts, with interpretable parameters; blind source separation gave 140 % higher material-classification accuracy in the robot experiment — [DiffImpact](https://par.nsf.gov/servlets/purl/10341944). Follow-on DiffSound (2024) adds a differentiable finite-element module for modal rendering — [DiffSound](https://arxiv.org/pdf/2409.13486).
- Games precedent: from one recorded impact, Lloyd et al. compute a modal model and synthesise variations on the fly. Using extracted mode amplitude envelopes directly often beats exponential-decay fitting. With a residual, results are "in most cases indistinguishable from recorded clips." It uses less console memory than multiple clips, has a simple-filter fallback for non-modal sounds, and shipped in Xbox 360's Crackdown II — [Lloyd, Raghuvanshi, Govindaraju, I3D 2011](https://microsoft.com/en-us/research/?p=309038).
- SoundSeed Impact splits a recording into noise-only residual plus a resonance data model, and changes modes in frequency and magnitude at runtime — [MCV](https://mcvuk.com/development-news/audiokinetic-unveils-soundseed/). Its author warned that modal synthesis suits some sounds better than others — [MCV](https://mcvuk.com/development-news/audiokinetic-unveils-soundseed/).
- Scale: Raghuvanshi & Lin ran up to "hundreds of sounding objects" at over 100 FPS. Over 100 metallic rings plus a table ran above 200 audio-FPS (one audio frame = sound worth one video frame at 100 FPS), and audio took 10 % of CPU in the xylophone scene on a 3.4 GHz Pentium 4. Mode compression, truncation and priority-based quality scaling gave up to an order of magnitude speedup. Impact and rolling emerge from one model driven directly from the physics mesh — [UNC Symphony](https://gamma.cs.unc.edu/symphony/).
- Eigenmode compression: hundredfold ratios without audible degradation (mode shape data, not the resonators) — [Langlois, An, Jin, James 2014](https://history.siggraph.org/?p=103520).
- Modal analysis is expensive and usually preprocessed; CPU limits the number and complexity of objects, and a GPU implementation allows many more — [Rausch, RWTH thesis](https://publications.rwth-aachen.de/record/721513).
- Physical simulation of aerodynamics, liquids and similar can be extreme offline: Farnell says such models "need a rack of computers that take days to process a few seconds of sounds" — [Farnell interview](https://designingsound.org/2012/01/18/procedural-audio-interview-with-andy-farnell/). Harmonic Fluids and Sounding Liquids are the research reference — [Harmonic Fluids](https://research.cs.cornell.edu/HarmonicFluids/harmonicfluids-lowres.pdf), [Sounding Liquids](https://gamma.cs.unc.edu/SoundingLiquids/soundingliquids.pdf).
- Fournel separates the excitation signals for impacts (hitting) and friction (scraping/rolling/sliding), with an interface to the physics engine/collision manager — [Fournel](https://cedec.cesa.or.jp/2010/archive/files/C10_P0051/C10_P0051.pdf).

### Inferences
- **Practical mapping for a 2D editor with no 3D mesh.** Do not run FEM. Use per-material mode tables (frequency ratios, decay, gain), scaled by an object-size parameter, so no modal analysis stage is needed at runtime.

| Input | Drives | Audible effect |
|---|---|---|
| Normal impulse/relative velocity | Exciter gain m | Loudness, plus more modes audible |
| Velocity and hardness | Contact time τ | Brightness (short τ excites high modes) |
| Material | d_k, frequency ratios | Decay and inharmonicity |
| Size/area | f_k scale, d_k scale | Pitch and length |
| Contact point (fraction along shape) | g_k per position | Timbre variation (DiffImpact ignores it; Faust bells use 7 positions) |
| Sliding speed + contact duration | Friction noise exciter | Scrape/roll instead of hit |

- A 2D rigid-body engine provides impulse and contact events cheaply. Rapier is the host's engine — [CLAUDE.md §5](/home/enio/Documentos/Projetos/PH2D/CLAUDE.md). Rate-limit and rank contacts by priority, following Raghuvanshi's quality scaling, or contact chatter will produce machine-gun retriggering.
- Offline use of a DiffImpact-style fit (one or many recordings → mode tables) is more attractive than ML generation: output is small, interpretable and deterministic at runtime. The fit is the part that depends on an ML stack.

## How can sound be derived from non-audio data?

### Takeaway
Three mappings fit the host: **image as spectrogram** (paint → oscillator bank), **events as exciters** (physics contacts, particle births → grains/modes), and **curves as control signals** (motion/animation values → synth parameters at a chosen rate). The last two have no authoritative recipe in the literature searched but follow directly from cited models.

### Cited Findings
- Image as spectrogram: Photosounder imports JPEG/PNG/BMP and synthesises it directly. Its Steam listing showed a planned release of 11 Aug 2026; current status unverified — [Steam](https://store.steampowered.com/app/4923680/Photosounder/).
- Phosphor (RoEx, macOS): brightness → loudness, vertical → pitch, horizontal → time — [Synthtopia](https://www.synthtopia.com/?p=152404). SonicPhoto: each pixel is a harmonic source, scanned left to right — [CDM](https://cdm.link/sonicphoto-focuses-on-transforming-images-into-sound-with-precision-harmonies-stereo-windows/).
- Non-scanning alternative: an ICAD paper sonifies chosen image regions instead of scanning left to right — [McGee, ICAD 2012](https://3a.ro/wp-content/uploads/2016/07/McGee_ICAD_2012.pdf).
- Painting a magnitude spectrogram needs phase. Griffin-Lim iterates STFT/ISTFT while holding magnitude fixed; it decreases the objective and converges to a stationary point, but often fails to recover the true signal — [Deep Griffin-Lim](https://arxiv.org/pdf/1903.03971), and produces extra reverberation and phasiness — [arXiv 1804.02181](https://ar5iv.labs.arxiv.org/html/1804.02181). `librosa` offers a "fast" momentum variant and random initialisation by default — [librosa](https://librosa.org/doc/dev/api/generated/librosa.griffinlim.html).
- Physics and motion as drivers: Fournel names rolling-ball and motion-controller sounds as good procedural candidates and whooshes as an "ideal candidate for motion controllers" — [Fournel](https://cedec.cesa.or.jp/2010/archive/files/C10_P0051/C10_P0051.pdf). Farnell notes a single vehicle model can encode speed, size and direction, which is hard with samples — [Farnell interview](https://designingsound.org/2012/01/18/procedural-audio-interview-with-andy-farnell/).
- Rate of control: MetaSound triggers run sample-accurately (1/48 000 s, 0.02 ms) and many node parameters can be modulated by audio buffers — [Epic MetaSounds](https://dev.epicgames.com/documentation/en-us/unreal-engine/metasounds-the-next-generation-sound-sources-in-unreal-engine).
- Host context: Motion Nodes (dynamics with a GPU cook), Rapier physics, Flip strokes, Painter and Timeline signals already exist in the app — [CLAUDE.md §5](/home/enio/Documentos/Projetos/PH2D/CLAUDE.md).

### Inferences
Mapping proposal for this host (design ideas, unverified by smoke or measurement):

| Host data | Sound use | Technique |
|---|---|---|
| Painter/Pixel layer | Spectral painting: x time, y log-frequency, luminance amplitude, optional hue → pan or noisiness | Additive oscillator bank or noise-band bank; no phase retrieval needed |
| Layer stack | Each layer = one sound layer, with blend mode as spectral operation | Spectral masks and cross-synthesis |
| Brush stroke | Pressure → amplitude, speed → grain rate, direction → pitch bend | Control signal into granular or noise model |
| Motion Nodes particles | Birth = grain or bubble; size → frequency (Minnaert-style); speed → gain | PhISEM-like event stream, population not per-particle voices |
| Rapier contacts | Impact and scrape exciters | Modal + friction noise (previous section) |
| Skeleton/Timeline curves | Curve value and derivative → filter, pitch, whoosh gain | Whoosh ∝ speed; animation markers fire events |
| Vector shapes/outline | Polygon as a single-cycle wavetable; area → pitch | Wavetable, novelty value |

- Prefer additive or filter-bank rendering for painted spectra over Griffin-Lim: phase is free for synthetic content, and iterative phase retrieval brings the phasiness the literature warns about, plus nondeterminism if initialised randomly without a fixed seed.
- Particle data must be aggregated (statistics to events). Mapping every particle to a voice will not scale; PhISEM's whole argument is statistical replacement of per-bead simulation.
- Sound must be sampled from a fixed simulation clock, not from the frame rate, or a recipe will vary with FPS. See the determinism section.

### Gaps
- Searches found no primary source on sonifying particle systems, physics simulation or animation curves for game SFX. Treat the table above as design hypothesis.
- No perceptual evaluation of image-to-sound for SFX usefulness was found. Tools are demonstrated, not assessed.

## Variation, runtime versus baked, and delivery to games

### Takeaway
Runtime engines want short SFX at low decode cost and longer material compressed. Standard variation (shuffled round robin + pitch/volume) does not change timbre, whereas seeded recipes do, so a seeded recipe either bakes N varied files or ships as runtime synthesis. The loudness target applies to the game mix: **−24 LUFS ±2 console, −18 or −16 mobile, −1 dBTP** at most.

### Cited Findings
**Variation**
- Scripting solutions offer randomised assets, volume/pan/pitch variation and streaming, with "no timbral modifications" and still large resource use — [Fournel](https://cedec.cesa.or.jp/2010/archive/files/C10_P0051/C10_P0051.pdf).
- A community Wwise example is 15 wood-footstep variations in shuffle, avoiding the last 10 — [Audiokinetic Q&A](https://blog.audiokinetic.com/qa/3617/routing-puzzle-impossible-to-solve) (one user's configuration, not a recommendation). Unity's Random Audio Container guidance notes one or two samples of a set often stick out as too loud — [Game Dev Beginner](https://gamedevbeginner.com/how-to-use-the-random-audio-container-in-unity/).
- Modal-model variation is shown to be viable in shipped console titles — [Lloyd et al.](https://microsoft.com/en-us/research/?p=309038). MetaSound Presets override a graph's inputs, avoiding "hundreds of potentially similar graphs" — [Epic](https://dev.epicgames.com/documentation/en-us/unreal-engine/metasounds-the-next-generation-sound-sources-in-unreal-engine).

**Loops**
- Prefer engine-native loop points inside one file over replaying on completion, because callbacks add latency — [Bugnet](https://bugnet.io/blog/how-to-loop-game-music-without-pops). Equal-power crossfade at the seam; 10–30 ms for dry, drum-heavy material — [HackerNoon](https://hackernoon.com/how-to-turn-an-ai-generated-track-into-a-seamless-game-loop-with-ffmpeg-godot-unity-and-web-audio). Practical guides, not primary sources.
- MP3 encoders add padding that leaves gaps unless metadata is honoured; Ogg/WAV are recommended for loops — [Elecbyte](https://elecbyte.com/mugendocs/loopguide.html). Hardware decoders may have limits such as sample-accurate looping — [Audiokinetic codec guide, via extract](https://www.audiokinetic.com/en/blog/a-guide-for-choosing-the-right-codec).

**Runtime versus baked**
- MetaSounds: a DSP rendering graph per sound, rendered in parallel asynchronously, each its own engine that converts to an optimized static non-virtual C++ object; may use different sample rates and buffer sizes; custom inputs from Blueprint/C++ — [Epic](https://dev.epicgames.com/documentation/en-us/unreal-engine/metasounds-the-next-generation-sound-sources-in-unreal-engine).
- Farnell estimates one or two cores of eight for a fully procedural soundscape, and argues the barriers are "structural and political"; an estimate, not a benchmark — [Farnell interview](https://designingsound.org/2012/01/18/procedural-audio-interview-with-andy-farnell/).

**Loudness**
- PlayStation: −24 LUFS integrated ±2 LU console, −18 ±2 portable, max −1 dBTP, LRA cap 20 (as of Feb 2024, secondhand) — [Audiokinetic, Mastering a Game, via extract](https://audiokinetic.com/ko/blog/mastering-a-game-with-wwise-part1).
- ITU report: typical video game level −24 ±2 LKFS console, −18 ±2 portable — [ITU-R BS.2434-0 (2018)](https://www.itu.int/dms_pub/itu-r/opb/rep/R-REP-BS.2434-2018-PDF-E.pdf). **Conflict:** the Audio Gang IESD sheet says −24 LUFS ±2 and ≤ −1 dBTP for console, measured with BS.1770-3, but **−16 LUFS ±2** with LRA 10–15 LU for mobile/handheld (v03.02, 2015) — [IESD](https://www.audiogang.org/wp-content/uploads/2015/04/IESD-Mix-Ref-Levels-v03.02.pdf).
- Meta recommends −16 LUFS for standalone and −18 for PCVR — [Meta](https://developers.meta.com/vr/documentation/unreal/audio-loudness-meter-overview/). An older console figure of −23 LUFS for PS3 also circulates — [Designing Sound](https://designingsound.org/2013/02/20/different-loudness-ranges-for-console-and-mobile-games).

**Formats and decode**
- Wwise codecs: PCM, ADPCM, Vorbis, Opus. Vorbis roughly 2:1–40:1, Opus 2:1–60:1, better on voice and some music. WEM Opus is not on every platform (Switch column shows No, PS5 shows 80 streams; garbled table, verify) — [Audiokinetic codec guide, via extract](https://www.audiokinetic.com/en/blog/a-guide-for-choosing-the-right-codec). Audiokinetic staff advise ADPCM/PCM for very short files — [Audiokinetic Q&A](https://www.audiokinetic.com/qa/12760/computation-vorbis-decoding-possible-decompressed-memory).
- Unreal: Bink supports all features on all platforms; RAD Audio is similar in CPU at higher quality, rates limited to 48/44.1/32/24 kHz; ADPCM ~4× fixed quality; PCM cheap but memory-heavy; PlatformSpecific lacks seeking — [Epic ESoundAssetCompressionType](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/ESoundAssetCompressionType).
- Unity load types: CompressedInMemory decodes on play; DecompressOnLoad has very low playback CPU; Streaming uses least memory with a short buffer — [Unity AudioClipLoadType](https://docs.unity3d.com/ja/ScriptReference/AudioClipLoadType.html).
- **Opus vs Vorbis CPU conflict:** a 2011 Monty post says Opus reaches Vorbis quality at lower CPU and memory — [Xiph list](https://lists.xiph.org/pipermail/vorbis/2011-August/027602.html). A Factorio forum test found Opus decode considerably slower, and that scale was disputed — [Factorio forum](https://forums.factorio.com/viewtopic.php?p=579946). Measure it.

**Budgets**
- Scars Above: 250 MB audio memory cap on lower-spec hardware; audio thread under 50 % average on Gen 8, under 30 % on Gen 9/PC — [Audiokinetic, via extract](https://audiokinetic.com/en/audio-optimization-practices-in-scars-above).
- Physical voices around 150 on Switch per Audiokinetic staff guidance; decoding becomes a main cost at around 1000 voices — [Audiokinetic Q&A](https://www.audiokinetic.com/qa/12760/computation-vorbis-decoding-possible-decompressed-memory). Single-source, community-grade.
- Heavenly Sword held ~30 MB of whooshes on disk, ~3 MB resident at all times — [Fournel](https://cedec.cesa.or.jp/2010/archive/files/C10_P0051/C10_P0051.pdf). LittleBigPlanet PSP's physics bank used 85 waveforms and 60 complex scripts — same deck.

### Inferences
**Delivery recommendation (judgement).**
- **Baked default:** render recipe + seed list into WAV 48 kHz at design time, with a sidecar giving loop points and metadata. Export round-robin sets of N seeds, each with bundled pitch/volume ranges. A "loudness-matched set" fixes the problem of a sample sticking out.
- **Export codecs:** WAV (for handoff to any engine), Ogg Vorbis/Opus for size. The PH2D audio module already exports Ogg/Opus — [CLAUDE.md §5](/home/enio/Documentos/Projetos/PH2D/CLAUDE.md).
- **PH2D's own game runtime:** can run recipes directly, using each voice's RTPCs for physics-driven classes (impacts, scrapes, wind, engines, whooshes). Decide per class by the Fournel criteria.
- **Hybrid:** bake at load time or level load into a cached buffer, cutting playback CPU to that of PCM while keeping the small on-disk recipe.
- **Asset-level loudness:** normalise SFX by class (e.g. UI vs impact relative levels), leaving the mix to reach the integrated target. Preview by metering peak, short-term and integrated, with a −1 dBTP ceiling warning.
- **Loops:** recipe loops can be made from phase-continuous parameters or a crossfade baked in; loop points must survive export.

| Situation | Choice |
|---|---|
| Very short, frequent, must be cheap | PCM or ADPCM baked |
| Medium SFX, size matters | Vorbis/Opus/Bink baked, decoded in memory |
| Long ambience | Streamed, or a recipe if noise-based |
| Physics-driven, or continuous parameter | Runtime synthesis |
| Must sound exactly the same on all targets | Bake once, ship PCM or compressed (subject to the codec's own determinism) |

## What can be deterministic, and how big is the recipe-versus-sample benefit?

### Takeaway
A recipe can be byte-identical across machines if the render path uses only IEEE basic arithmetic, its own sin/exp/pow, a seeded PRNG, fixed-order mixing and no FMA contraction. By my arithmetic, a recipe is about 1–2 orders of magnitude smaller than a compressed variation set, and much less so against a single short sound. The advantage shrinks once you count the synth runtime, and it disappears in the shipped game if the sounds are exported as baked files.

### Cited Findings
**What is and isn't guaranteed**
- Rust: +, −, ×, ÷ are correctly rounded per IEEE 754-2008 (roundTiesToEven). `sin`, `cos`, `exp`, `powf` have "non-deterministic" precision that varies by platform and Rust version, and "can even differ within the same execution." NaN bit patterns are not portable. `mul_add` is the rounded infinite-precision result, guaranteed not to change — [Rust f32 docs](https://doc.rust-lang.org/std/primitive.f32.html).
- Gaffer: across compilers and architectures it is "incredibly naive" to expect identical results from arbitrary floating-point code; libm functions are not bit-specified, AMD and Intel differed on trig in Battlezone 2; strict modes disable FMA contraction and value-changing optimisations; iteration counts dependent on CPU speed break determinism; Maclaren says strict reproducibility is "effectively incompatible with most forms of parallelism" — [Gaffer on Games](https://gafferongames.com/post/floating_point_determinism/).
- FMA changes the last bit when `a*b + c*d` uses one rounding instead of two — [Poncelet wiki](https://github.com/FelixMiddelhoff/poncelet/wiki/BitExact-FMA-Bug-Hunt).
- **Direct audio precedent:** `tono-core` routes byte-pinned render paths through its own deterministic kernels, keeps platform libm only for analysis and authoring (outside its byte-identity promise), keeps old engine versions on old kernels so historical renders stay bit-exact, and precomputes filter constants — [tono-core dsp.rs](https://docs.rs/crate/tono-core/latest/source/src/dsp.rs).
- Pure-Rust `libm` was reported sufficient between Linux and macOS in one user's tests only — [Rust forum](https://users.rust-lang.org/t/f64-ln-1p-platform-specific-behavior/77113). XMOS aims for bit-exact fixed-point int32 between Python and C — [XMOS](https://www.xmos.com/documentation/XM-015103-UG/html/doc/05_api_reference/modules/index.html).
- **Encoders are not automatically deterministic:** WEM Opus output differed between Intel and AMD in Wwise 2021.1, with a fix planned for 22.1 — [Audiokinetic Q&A](https://www.audiokinetic.com/qa/10665/wem-opus-differs-when-generated-on-intel-and-amd-x64-cpus).
- **Project precedent:** the Painter has this law for CPU strokes: "same stroke, same byte", using `ph2d_det_math::DetMath` (`det_sin`, `det_powf`) under the census `o_motor_nao_chama_a_libm_do_sistema`, after a glibc version changed bytes (Bug #58). It applies only to the CPU stroke — [project memory](/home/enio/Documentos/Projetos/PH2D/project-memory/project_same_stroke_same_byte_on_any_machine_2026_11_04.md).
- ZzFX's micro version calls `Math.random()`; its seed behaviour depends on using `ZZFX.R()` instead — [ZzFX README](https://github.com/KilledByAPixel/ZzFX/blob/91418012bcc12c1abb3b1141a104b71a6e5e7215/README.md). It shows that "a recipe" does not imply reproducibility.
- **LOCAL MEASUREMENT:** a 32-mode f32 modal kernel hashed FNV-1a identically (`75576087e99ab784`) at `opt-level=0`, `-O` baseline, and `-O -C target-cpu=native` on this Ryzen 9950X. It shows no FMA contraction or autovectorisation effect in `rustc` output for this kernel. It says **nothing about other CPUs or libcs**, since setup coefficients used `std` `exp`/`cos`.

**Size**
- Farnell: a procedural sound "occupies 4kb and plays for six hours" — [Farnell interview](https://designingsound.org/2012/01/18/procedural-audio-interview-with-andy-farnell/).
- .kkrieger: 96 KB FPS, relying on procedural asset generation — [Activision Blizzard](https://newsroom.activisionblizzard.com/p/a-brief-history-of-the-worlds-smallest). ZzFX's engine is under 500 bytes in the micro version — [ZzFX README](https://github.com/KilledByAPixel/ZzFX/blob/91418012bcc12c1abb3b1141a104b71a6e5e7215/README.md). One demoscene group computes its music in real time on a separate thread filling the audio buffer — [Laurent Le Brun](https://medium.com/@laurentlb/how-can-demoscene-productions-be-so-small-663c0064e512).
- Lloyd et al. report less memory than multiple clips, but no figure — [Lloyd et al.](https://microsoft.com/en-us/research/?p=309038).

### Inferences
**Size arithmetic (my calculation; assumes 48 kHz 16-bit mono, and a mid-range 10:1 codec from within the cited 2:1–40:1 band).**

| Item | Bytes |
|---|---|
| 1 s PCM | 96 000 |
| 1 s at 10:1 | 9 600 |
| 15 footsteps of 0.4 s, PCM | 576 000 |
| Same, at 10:1 | 57 600 |
| 32 modes as 3 × f32 | 384 |
| Plausible full recipe (graph + params, JSON or binary) | 200–4 000 |
| Same 15 footsteps as one recipe + 15 seeds | ≈ the recipe + 60 |
| Farnell's 6 h of PCM equivalent | ≈ 2.07 GB, if the output is genuinely non-repeating |

Ratios, using the 200–4 000 byte recipe plus 60 bytes of seeds: a **15-variant set is about 14–220× smaller than the compressed set and 140–2 200× smaller than PCM. A single 1 s sound gains only about 2.4–48× and 24–480×.** The win comes from variation, and all of this is before the synth runtime, whose cost is shared across all sounds. Where the host app already embeds its runtime, the marginal cost per sound is the recipe alone. Exported to third-party engines as baked assets, **the size benefit goes away in the shipped game**, and only source-project size and regeneration remain. Recipes are worthless if their dependent samples ship anyway: count samples referenced by the recipe.

**What can be pinned (design proposal).**

| Layer | Deterministic? | How |
|---|---|---|
| Parameters, seed, recipe format | Yes | Versioned schema, little-endian, no floats printed as text unless round-trippable |
| PRNG | Yes | Own xorshift/PCG family, per-voice substream |
| + − × ÷ sqrt kernels | Yes | IEEE; avoid implicit contraction, and pin `mul_add` use consistently |
| sin/exp/pow/tanh | Only with own code | Reuse `ph2d-det-math` or tables |
| Sample-rate conversion, FFT | Yes if own/pinned | No system FFT or BLAS whose build varies |
| Mixing voices | Yes if fixed order | Render in parallel, sum in a fixed index order |
| Timing | Yes if sample-indexed | Events keyed to samples, independent of the block size and frame rate |
| Denormals | Risky | Handle with an explicit gate/threshold, not FTZ/DAZ settings that vary by thread |
| GPU DSP | No | Keep the render law on the CPU, matching the Painter |
| External engines, encoders | Not by default | Hash PCM before encoding, not the encoded file; pin the encoder if encoded bytes matter |
| ML generation | Not by default | Bake the result and treat it as a sample |
| Runtime synthesis with live game inputs | Only given identical inputs | Same recipe + same event log = same output; live physics is its own issue |

- Add a **render-engine version field** to each recipe, following `tono-core`: a change in kernels must not silently change old sounds. A golden-hash test per factory recipe parallels the project's brush alarm approach.
- Compare hashes across at least one Intel and one AMD or ARM machine in CI before claiming "every machine". This has not been done here.

### Gaps
- No primary published measurement of recipe vs sample size for a real shipped game was found; Lloyd gives none and the table above is my arithmetic.
- No standard or peer-reviewed reference on bit-exact audio synthesis across platforms was found; evidence is project docs and forum posts.
- `tono-core`'s maturity and adoption were not assessed. Read as a design precedent only.
- V2 synth (.kkrieger) details rest on one weak source, so I excluded them. Search did not confirm sfxr's Ludum Dare origin or jsfxr's URL parameter encoding.
